RainScope is a precipitation forecast map backed by ECMWF Open Data IFS and AIFS GRIB2 products.

Metres are converted to millimetres; `kg m**-2` is numerically equivalent to millimetres of water. The API preserves the GRIB parameter, level, units, step type, run/valid times, interval, grid, dimensions, and file hash. Missing-value sentinels and non-finite values render transparent, while zero precipitation has a light visible tint.

Both IFS and AIFS Single were retrieved and decoded live for this run (verified source evidence). The app only displays a forecast after a real GRIB has been retrieved or validated from cache; it shows an unavailable message when the selected run cannot be served and never substitutes demo values. The current verification environment does not provide a browser for visual canvas inspection and blocks requests to the OSM tile host, so basemap and overlay appearance still require a browser check on a network where the configured tile provider is reachable.

The map can show either a single model's accumulated precipitation or **model disagreement (AIFS Single − IFS)**. The comparison is only produced when both real GRIBs share the same run, valid time, accumulation interval, dimensions, grid type, and aligned coordinates; both inputs are normalized to millimetres first. The difference is a deterministic model-to-model difference, not probability or confidence. Clicking the map samples the nearest GRIB grid point and returns a six-hour timeline. When a model supplies cumulative 0–N hour fields, adjacent intervals are calculated by differencing consecutive cumulative totals; the native GRIB intervals and method are included in the API response. Point timelines currently cover forecast hours 6–72.

The interface labels whether each field was retrieved live or served from cache, along with its source run, valid time, accumulation interval, source units, converted units, GRIB parameter/step type, and retrieval timestamp. Cached fields are the original validated GRIB files, not generated forecast substitutes.

Forecast reports default to the selected place’s local IANA time zone and show UTC alongside it; UTC remains the stored and calculated reference. Users can choose UTC or device time in Settings. `/api/timezone` resolves coordinates locally through `timezonefinder`; coordinates are not sent to a time-zone service. Search results may also retain the IANA time zone returned with the explicitly submitted place-name search, so a selected searched place can still show local time if the offline lookup package is unavailable. This sends a place name to Open-Meteo Geocoding, never saved coordinates for timezone lookup. My location, manually entered coordinates, and map-picked points require the offline boundary package and otherwise show UTC with an explicit notice. The timezonefinder library is MIT licensed, while its bundled boundary data is separately licensed under ODbL and derived from OpenStreetMap through timezone-boundary-builder. The project pins `timezonefinder-data==4.2026.5`; where the dataset reports overlapping boundary polygons, RainScope shows the primary zone and the other matching zones. The lookup uses full input coordinates (not rounded coordinates) and stores no resolved zone in forecast data. See the [timezonefinder usage and boundary behavior](https://timezonefinder.readthedocs.io/en/latest/1_usage.html), [license and data provenance](https://timezonefinder.readthedocs.io/en/latest/3_about.html), and [pinned data release](https://pypi.org/project/timezonefinder-data/4.2026.5/).

## Product pages

On a clean Overview visit, RainScope first asks the API for validated cached fields and selects the newest past run/lead found there. If no validated cache exists, it does not issue a forecast request for a guessed default or display demo values; it shows a retryable first-run state while keeping the global basemap and explicit place/geolocation actions available. Explicit shared URL selections are preserved and validated independently. The site includes Overview, Explore Map, Compare Models, Rain Planner, Locations, Forecast Changes, Data & Method, and Settings at `/`, `/map`, `/compare`, `/planner`, `/locations`, `/history`, `/data`, and `/settings`. Forecast selections are carried in the URL. Saved places and display preferences stay in browser local storage. Startup validates URL selections and saved place records; unsupported entries are kept in storage but not used, and an unreadable storage payload is left untouched. Unexpected route render failures are reported inside the app shell so navigation and unaffected pages remain available. Direct refreshes of `/` and `/map?...` return the app shell under Vite preview; deployed static hosts must configure an SPA fallback that serves `index.html` for application routes. The shared UTC cycle selector refreshes validated availability when the selected model or date changes. A cycle is usable only when a validated cached GRIB exists for the exact selected lead; an explicit ECMWF check can validate an uncached lead, and changing runs requires a deliberate selection. Availability is independent of location, and a cycle switch clears prior-run values before reloading the map, point outlook, and planner. The map timeline follows each model/cycle's supported forecast leads. Point series and location planning cover six-hour leads through forecast hour 72. The Overview saved-place card leads with a location pin and place name, shows a model-derived precipitation summary when validated point data exists, and keeps coordinates in a secondary disclosure. When consecutive selections are comparable, the map page reports the difference between cumulative totals at the selected place using same-model, same-run, same-grid GRIB fields with validated 0–lead accumulation intervals; otherwise it explains why a difference is unavailable. The rain legend uses the backend's fixed 0, 1, 5, 10, and 25 mm color stops and labels the selected GRIB interval.

## AI and automation

RainScope uses deterministic, inspectable summaries rather than a language model. Overview and Planner totals, threshold crossings, and wettest-period labels are calculated from validated ECMWF point-series responses; missing values are excluded, and the source forecast metadata remains available beside the summaries. No forecast values or coordinates are sent to an AI provider. The frontend requests data when a page or user selection needs it, and the API deduplicates concurrent retrievals and validates cache entries. There is no scheduled ingestion worker, guaranteed refresh cadence, or notification delivery service in this project. Those capabilities are deferred because they require a continuously operated backend worker, bounded operational retries, and a reliable delivery channel that are not part of the current deployment. No deterministic model disagreement is presented as probability or confidence.

Forecast Changes compares runs only when both validated GRIBs are already cached and have the same valid time and the same absolute accumulation start/end times. The run-relative GRIB step ranges may differ between cycles; the API maps those ranges onto UTC before deciding whether they cover the same precipitation period. Grid coordinates, dimensions, parameter, level, step type, and original units must also match. The selected-place view reports both sampled totals, source runs, retrieval times, and the newer-minus-older difference only when both runs resolve to the same non-missing grid cell. Otherwise it explains why the point comparison is unavailable. It does not download older runs or fabricate a change map. AIFS ENS, ensemble probabilities, and run-to-run comparisons without comparable cached fields are not presented as supported data.

The current ECMWF Open Data catalogue documents IFS `tp` at 0.25° and 0.1° resolution; this app requests 0.25°. IFS forecast leads run 0–144 h every 3 h for all four cycles; 00/12 UTC additionally offer 150–360 h every 6 h. AIFS Single `tp` is available every 6 h through 360 h. The selector and API enforce those model/cycle schedules. ECMWF says the Open Data archive is rolling (most recent 12 runs, roughly 2–3 days), and publication timing differs by product/resolution. Documentation is not proof a particular file is online: a selected lead is served only after retrieval and GRIB validation.

ECMWF Open Data are licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) and the [ECMWF Terms of Use](https://apps.ecmwf.int/datasets/licences/general/). The app displays the required source acknowledgement: “This output is based on data and products of the European Centre for Medium-Range Weather Forecasts (ECMWF).” ECMWF Open Data catalogue: https://www.ecmwf.int/en/forecasts/datasets/open-data

## Run locally

Start the backend in Terminal 1. Bind to loopback so the API is not exposed to the local network:

```sh
cd /home/gowtham_kishore/projects/rainscope
conda activate rainscope
python -m pip install -r requirements-dev.txt
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --reload
```

Start the frontend in Terminal 2. Set its API target explicitly. Vite is configured to bind only to `127.0.0.1:5173` and fail rather than silently selecting another port; its startup log prints the `/api` proxy target:

```sh
cd /home/gowtham_kishore/projects/rainscope/frontend
npm ci
RAINSCOPE_API_PROXY_TARGET=http://127.0.0.1:8000 npm run dev
```

Open `http://127.0.0.1:5173/`; Vite proxies `/api` to the FastAPI process at `http://127.0.0.1:8000`. Stop each server with Ctrl+C in its own terminal. If startup reports an occupied port, identify its owning process before stopping anything; do not start another Vite instance on an automatically selected port. Verify the API identity at `/api/health` and readiness at `/api/ready`. Run backend tests from the repository root with `python -m pytest -q`; run frontend tests and a production build from `frontend/` with `npm test` and `npm run build`.

### Production deployment

A local production container setup is provided in `Dockerfile`, `frontend/Dockerfile`, `compose.yaml`, and `deploy/nginx.conf`. It builds the locked React frontend, runs FastAPI with Python 3.12 and ecCodes, provides same-origin `/api` routing and SPA fallback, and persists validated GRIB/raster cache data in a named volume. See [DEPLOYMENT.md](DEPLOYMENT.md) for configuration, startup, backup, update, rollback, health checks, and provider limitations. The setup has not yet been built or smoke-tested in this environment; do not treat its presence as a deployment verification.

The map defaults to the OpenFreeMap Liberty style (`https://tiles.openfreemap.org/styles/liberty`), whose style supplies attribution to MapLibre. Its terms (checked 6 November 2026) provide the public service as-is, without a service guarantee; review the current [Terms of Service](https://openfreemap.org/tos/) before deployment. To override it with a custom style URL, set `VITE_BASEMAP_STYLE_URL` and the provider's required `VITE_BASEMAP_ATTRIBUTION`; for raster tiles, set `VITE_BASEMAP_TILE_URL` and `VITE_BASEMAP_ATTRIBUTION`. Follow the provider's terms, attribution, and caching rules. Missing attribution, tile/style request failures, and MapLibre raster-source failures are surfaced in the map; the precipitation API and raster remain independently available.

Location controls are explicit and local-first. Browser geolocation runs only after the user activates the location button; coordinates are saved in browser local storage only after the user chooses “Save and select My location.” Overview, Compare, Rain Planner, and Locations share the same Open-Meteo Geocoding picker. It sends no request until at least three letters or numbers are entered, waits 350 ms after typing pauses, aborts obsolete requests, and displays at most five deduplicated results. Typing never requests a forecast; selecting a result saves its display name and exact coordinates together, then updates the selected location. The [Open-Meteo Geocoding API](https://open-meteo.com/en/docs/geocoding-api) attributes place data to [GeoNames](https://www.geonames.org/). Its free API is for non-commercial use under CC BY 4.0; current terms list limits of 10,000 requests/day, 5,000/hour, 600/minute, and 300,000/month (checked 6 November 2026; [current terms](https://open-meteo.com/en/terms)). A commercial deployment must choose a geocoder whose license permits that use.

Location forecast times default to the selected place’s IANA time zone, with UTC shown alongside. The `/api/timezone` endpoint uses offline `timezonefinder` boundary data and does not send coordinates to a geocoding or time-zone service. Install `requirements.txt` into the same active environment that runs FastAPI; having the dependency in the file alone does not make it available to an already-created environment. The lookup library is MIT licensed; its boundary data is separately ODbL licensed and derived from OpenStreetMap through timezone-boundary-builder. RainScope pins `timezonefinder-data` to 4.2026.5 for repeatable lookups. A place selected from an explicit Open-Meteo name search can use the IANA zone in that search result as a fallback; My location and coordinate-only places cannot. Exact points on disputed/shared boundaries can remain ambiguous; the UI names the selected zone and retains UTC as the calculation/reference time. If no valid zone is available, the interface falls back to clearly labeled UTC. Local rendering uses the browser’s IANA time-zone database, which applies daylight-saving rules for the selected zone.

FastAPI's interactive schema is available at `http://localhost:8000/docs`. First-party endpoints are `/api/health`, `/api/ready`, `/api/catalog`, `/api/availability`, `/api/timezone`, `/api/forecast`, `/api/forecast/raster`, `/api/point-series`, `/api/comparison`, `/api/comparison/raster`, `/api/history/candidates`, `/api/history`, `/api/history/point`, and `/api/history/raster`. JSON responses use Pydantic schemas; errors use an `{ "error": { "code", "message", "context" } }` envelope. Invalid and future selections return 422, unpublished ECMWF data returns 404, network/upstream failures return 503, GRIB validation failures return 502, and unaligned comparisons return 409. Missing history is reported separately and is never fetched implicitly.

## Forecast interpretation

The displayed field is total precipitation accumulated over the GRIB message's `startStep`–`endStep` interval, converted from the GRIB units to millimetres. It is not a precipitation rate. Forecast values are model output, not observations or a guarantee of local conditions. Availability, release timing, and supported steps depend on ECMWF's live dissemination and rolling archive.
